# 橘听优化方案（基于代码评审 · 2026-09）

> 定位：替代《橘听全维度架构优化与实施排期方案》的可执行版本。
> 与外部方案的区别：所有"现状痛点"均已对照真实代码核实（含 file:line 依据）；
> 数字基线先测后优化；优先级以"凭据安全 > 证据驱动的性能 > 架构演进"排序。

## 0. 方案原则

1. **先建基线，再谈优化**。外部方案的所有数字（5.5s 冷启动、350MB 显存、16~32ms 掉帧）均无测量依据，逐条核实后多数不成立。
2. **安全优先于性能**。当前同进程执行不可信第三方 JS，同时网盘 Cookie / WebDAV 密码 / 订阅令牌明文存 SharedPreferences，这是比任何性能项都高的风险。
3. **小步试点优于大迁移**。MMKV / Drift 这类存储重构必须单点试点、增量进入，禁止"全量切换"。

## Phase 0 · 基线测量（0.5 天，所有后续决策的输入）

| 指标 | 方法 | 通过线 |
| --- | --- | --- |
| 冷启动 | 真机 `adb shell am start -W` + `flutter run --profile` | 记录实际值；>2s 才值得做启动编排 |
| 目录滑动掉帧 | DevTools Timeline，后台播放 + 滑动 4000+ 集目录 | jank 比例与来源（是否存储） |
| 聚合搜索内存 | 10+ 源搜索，DevTools Memory | 是否有 OOM/尖刺（下采样已实现，预期无） |
| 被杀进度丢失 | 播放中最近任务划掉，重启测量偏差 | 记录实际丢失秒数（预期 ≤5s） |
| 切集空白 | 缓存命中/未命中两种场景分别测 | 命中场景预期已 <1s |

**产出**：`docs/baseline-2026-09.md` 一页纸。后续每个 Phase 的验收都对照这份基线。

## Phase 1 · 安全加固（约 3~4 人日，最高优先级）

### 1.1 凭据迁入安全存储
- **现状**：`webdav_service` / `baidu_pan_service` / `quark_pan_service` / `alist_service` / `webdav_sync_service` 的 Cookie、密码、订阅令牌全部明文存 SharedPreferences；`baidu_pan_service.dart` init 可见直接 `prefs.getString(_kConfig)`。
- **做法**：引入 `flutter_secure_storage`（Android 走 Keystore 加密）。迁移路径：读取旧 prefs 值 → 写入 secure storage → 删除旧键 → 服务 init 改读 secure storage。对同步加密口令同样处理。
- **验收**：`adb backup` / root 后 dump SharedPreferences 不再含任何 Cookie、密码、令牌；四个网盘 + 同步功能回归通过。

### 1.2 音源信任边界文档化 + 导入告警
- **现状**：QuickJS 桥接受控但非沙箱（架构文档自认）；恶意音源理论上可通过 `uni.request` 外传本机凭据。
- **做法**（不破坏现有源的兼容性）：① 在音源导入/订阅同步处提示来源与风险，显示音源声明的域名清单；② `JsEngine._handleHttp` 增加外发域名日志（脱敏），运行日志页可按源审计外联记录；③ 架构文档补充"信任模型"一节，明确边界 = 进程内、非沙箱。
- **验收**：导入第三方源时有风险提示；日志可回答"某源访问过哪些域名"。

### 1.3 顺手项
- CI 固定 Flutter 版本（当前用 master + `flutter upgrade`，构建不可复现）。

## Phase 2 · 快赢性能（约 2~3 人日，全部经代码核实为真）

### 2.1 聚合搜索并发池
- **现状**：`search_screen.dart:223` `await Future.wait(targets.map(_loadBucket))` 无界并发，源数量 = 并发量。
- **做法**：`package:pool` 限流 `Pool(3)`；每源独立超时（15s）防单源拖死整页。
- **验收**：10+ 源搜索时网络与 CPU 平稳；单源挂起不影响其它桶出结果。

### 2.2 聚合搜索结果缓冲刷新
- 做法：结果桶 200ms 窗口缓冲后批量提交 UI，避免每完成一个源全页重排。
- 验收：聚合搜索期间 Timeline 无连续重排尖刺。

### 2.3 运行日志升级为环形缓冲 + 导出
- **现状**：`LogService` 内存无上限，且进程死亡即丢失。
- **做法**：定长 ring buffer（建议 800 条）；设置页增加"导出诊断报告"（复制/分享，Cookie/Token 按现有脱敏规则过滤）。
- **验收**：长会话内存稳定；报告可直接贴 GitHub Issue 排错。

### 2.4 暂停超 30 分钟回退 5 秒起播
- 做法：恢复播放时判断暂停时长，`seek(max(0, pos - 5))`。
- 验收：长暂停后续播回到情节记忆点。

### 2.5 启动编排（条件执行）
- **现状**：`main.dart:51-118` 串行 await，但 `SourceManager.init`（source_manager.dart:175）与各网盘 init 实际只是读 SharedPreferences，**不存在外部方案声称的"JS 全量编译 1.8~2.5s"与"网盘握手 1.2~1.8s"**。真正偏重的是 `AudioService.init` 与数据库打开。
- **做法**：仅当 Phase 0 实测冷启动 >2s 时执行——把 `AudioService.init` 移到首帧后（现有 `_pendingResume` 设计天然兼容延迟加载），其余保持现状。
- **验收**：对照基线，冷启动下降幅度如实记录。

## Phase 3 · 播放与存储试点（约 5~8 人日）

### 3.1 MMKV 单点试点：播放进度热写入
- **范围严格限定**：只有"播放秒数"一个键迁入 MMKV（包名 `mmkv`，注意外部方案写的 `flutter_mmkv` 不存在），其余数据一律不动。
- **做法**：
  - 播放中每 1s 写 MMKV 键 `pos_{sourceId}_{bookId}`（同步写，天然抗杀）；
  - SQLite `play_progress` 维持现有节流写，作为慢副本与历史记录；
  - 续播恢复优先 MMKV、SQLite 兜底；`onHide`/`onPause`/耳机拔出时无需额外处理（MMKV 写即落盘）；
  - WebDAV 同步导出进度时合并 MMKV 热值（`webdav_sync_service` 已 import `progress_service`，在此处加一次读取）。
- **验收**：播放中强杀 App，重启进度偏差 <1s（对照 Phase 0 基线）；同步在两台设备间进度一致。
- **明确不做**：全量 SharedPreferences → MMKV 替换（迁移面大、收益未证实）。

### 3.2 下一集预解析（缩水版，不做 ConcatenatingAudioSource）
- **现状依据**：`CacheService` 已有"从当前集开始的后续章节自动缓存"，缓存命中时切集本就近乎即时；真正慢的是缓存未命中时的"解析直链 + 建连"。
- **做法**：`PlayerService` 监听剩余 ≤60s 时，后台预调用下一集 `getAudioUrl`（仅解析，不预拉字节）；命中已缓存章节则零成本。网盘短效直链不做预解析（会过期），交给 3.3 的代理根治。
- **验收**：JS 源缓存未命中场景切集空白下降（对照基线如实记录）。

### 3.3 本地回环流代理（网盘直链自愈，可选）
- **做法**：`shelf` 起本地 `127.0.0.1` 服务，注入防盗链 Header；网盘直链 401/403 时静默换链 302 重定向。注意点：networkSecurityConfig 需允许 loopback 明文；HLS 分片与 Range 透传单独处理。
- **验收**：伪造过期夸克/百度直链，播放不中断。工作量超预算则降级，只做百度/夸克两个最常出 403 的服务。

## Phase 4 · 架构演进（季度级，逐项立项，不排死期）

### 4.1 Repository 层（前置必做）
- 页面 → Repository 接口 → Service。这是解耦的第一刀，也是未来 Drift 迁移的成本转换器。顺带让 `PlayerService` / `SourceManager`（1412 行）的核心逻辑可单测。

### 4.2 网盘 Provider 接口
- WebDAV/AList/百度/夸克四个 Service 约 2400 行重复实现鉴权、目录→Book/Chapter 映射、封面缓存；统一接口后收敛为一处。新增网盘（以及 3.3 代理）成本从"再抄 600 行"变为"实现接口"。

### 4.3 JS Isolate 沙箱（先 spike 再立项）
- **真实痛点**：QuickJS 经 flutter_js 在 UI 线程同步执行，劣质源死循环会 ANR——这个成立。
- **两步走**：
  1. **Spike（2~3 天）**：验证 flutter_js 在后台 Isolate 可用性（platform channel 需 `BackgroundIsolateBinaryMessenger`；`rootBundle`/Dio 在子 isolate 的行为）；
  2. **正式实现（8~12 人日）**：worker 池 + 硬超时强杀 + **重点设计桥接迁移**——`uni.request`/crypto 回调现在挂在主 isolate 的 Dio 上（js_engine.dart），必须在子 isolate 内重建，这是工作量大头。
- **明确纠正外部方案**：Isolate **不能**兜住 QuickJS 原生崩溃（SIGSEGV 杀全进程，isolate 是同进程线程）；原生崩溃隔离只能拆独立进程，除非 Phase 0/线上证据显示确有此类闪退，否则不做。
- 佐证注意：仓库内 `anr_2026-06-21` 的真实 trace 中无任何 QuickJS 栈帧且主线程空闲（libhoudini 模拟器）——立项前先在真机复现一次 JS 死循环 ANR。

### 4.4 Drift 增量评估（最后）
- 仅当：Phase 0 实测存储导致掉帧，或 repository 层就绪后团队决定换取类型安全与 `watch()` 响应式刷新。Drift 可打开现有 `tingshu.db`、逐表声明迁移，但仍属大动作，默认搁置。

## 明确不做清单（与外部方案的差异）

| 外部方案条目 | 结论 | 依据 |
| --- | --- | --- |
| 封面下采样防 OOM | **已实现**，跳过 | `cover_image.dart:42-43` 已有 memCacheWidth/Height |
| LRU 缓存淘汰 | **已实现**（cachedAt 排序 + 集数/空间双上限） | 架构文档 §9.4 |
| 冷启动 5~6s 基线 | **不成立**（init 均为 prefs 读取，无 JS 编译、无网盘握手） | source_manager.dart:175、baidu_pan_service.dart init |
| SQLite IO 导致 UI 掉帧 | **不成立**（sqflite 跑后台线程；Android 9+ 默认 compatibility WAL） | sqflite 文档 + source.android.com |
| Isolate 解决 SIGSEGV | **技术错误**，改为"仅解决 ANR + spike 前置" | Dart Isolate 为同进程线程 |
| MMKV 全量替换 / Drift 全量迁移 | **搁置**，改单点/增量路径 | 见 Phase 3.1 / 4.4 |
| `package:flutter_mmkv` | **包名不存在**（真包为 `mmkv`） | pub.dev |
